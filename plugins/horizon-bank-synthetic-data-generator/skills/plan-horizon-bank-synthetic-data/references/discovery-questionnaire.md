# Discovery questionnaire

Inspect first. Ask only questions that remain unresolved and ask them one at a time.

## 1. Experience and consumers

- What customer journey must the data prove?
- Which screens, prompts, tools, calculators, tests, jobs, or APIs consume it?
- Which fields are rendered directly, aggregated, searched, filtered, or mutated?
- What are the exact acceptance queries a reviewer will try?

## 2. Existing contract

- Locate types, schemas, serializers, database models, fixture loaders, and route validation.
- Record required fields, optional fields, enums, units, null behavior, stable IDs, and joins.
- Identify duplicated facts embedded in UI code, prompts, documentation, or test snapshots.
- Decide whether to preserve the native contract or add a canonical adapter.

## 3. Delivery

- Select JSON bundle, JSONL, CSV, SQLite, Mongo import, REST fixture, or a target-language module.
- Determine whether data loads at build time, process start, session start, or per request.
- Decide whether a database is seeded once, reset per test, or regenerated by seed.
- For an LLM, define the smallest context view and tool identifiers needed per task.

## 4. Time and state

- Choose a fixed scenario date for repeatable demos or rolling time resolved once per generation.
- Set history length, future bill horizon, pending/posted behavior, and timezone.
- Choose snapshot-only, regeneratable, or project-owned mutable state.
- Define how transfers, purchases, payments, disputes, and time advancement reconcile.

## 5. Population

- Select archetypes, weights, household/business relationships, optional modules, and overlays.
- Select small, medium, large, or exact customer/history/transaction counts.
- Decide which edge conditions must be easy to locate by ID.
- Avoid coupling demographic traits to risk, credit, pricing, eligibility, or fraud.

## 6. Generation and validation

- Use deterministic rules for financial facts.
- Choose template narratives or controlled LLM narrative slots.
- Require safe synthetic contacts and prohibit sensitive identifiers or credentials.
- Define formula checks, relationship checks, date checks, export parity, performance, and target-project tests.

## Required planning output

Return a brief containing the resolved config, a canonical-to-target field map, adapter behavior, state/time policy, acceptance queries, and validation commands.
